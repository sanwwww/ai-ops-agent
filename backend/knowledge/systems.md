# 系统资源与日志排查知识库

## CPU 使用率过高排查
CPU 打满的标准排查链路：1) top 找到占用最高的进程；2) 用 top -Hp 进程号 找到进程内最耗 CPU 的线程；3) Java 程序把线程号转十六进制后在线程栈里定位代码（jstack）；4) Python/Go 程序用对应 profiler 采样。常见原因：死循环、正则回溯、频繁 GC、高并发请求。如果是 us（用户态）高查应用代码，sy（内核态）高查系统调用和上下文切换，wa（IO 等待）高则问题在磁盘而非 CPU。

## 内存不足与 OOM 排查
内存问题排查：1) free -h 看可用内存，注意 Linux 的 buff/cache 会被自动回收，cache 高不是问题；2) available 很低才代表真缺内存；3) top 按 M 排序找内存大户；4) 进程被 OOM Killer 杀掉时，dmesg | grep -i kill 能看到记录。Java 应用关注堆内存（-Xmx 配置），Python 应用注意内存泄漏常用 tracemalloc 分析。swap 频繁使用会导致性能骤降，即使内存还没耗尽。

## 磁盘空间满排查
磁盘满的经典处理：1) df -h 看哪个挂载点满了；2) du -sh /* 逐层往下找大目录；3) 最常见的元凶：应用日志没轮转、core dump 文件、临时文件堆积。注意"文件已删除但空间未释放"的坑：进程还持有被删除文件的句柄，lsof | grep deleted 能找到，重启对应进程才真正释放。长期方案是配置 logrotate 日志轮转。

## 服务启动失败排查
服务起不来的通用排查步骤：1) 先看服务自己的日志（启动失败原因 90% 写在日志里）；2) 端口被占用：netstat 确认端口是否被其他进程占了，常见于重启时旧进程没退干净；3) 配置文件语法错误：改过配置后启动失败，先用服务自带的配置检查命令（如 nginx -t）验证；4) 依赖不可用：数据库连不上、依赖的中间件没起来，服务会启动超时退出；5) 权限问题：非 root 用户监听 80/443 端口会被拒绝。

## Nginx 常见故障
Nginx 排查要点：1) 改完配置先 nginx -t 语法检查，再 nginx -s reload 热加载；2) 502 看后端应用是否存活，upstream 地址和端口是否配对；3) 504 调整 proxy_read_timeout 或优化慢接口；4) 日志双日志：access.log 看请求到达情况，error.log 看错误原因；5) worker_connections 不够会报 "too many open files"，调整 worker_rlimit_nofile 和系统 ulimit。

## MySQL 连不上排查
MySQL 连接失败的分层排查：1) 服务是否在跑：systemctl status mysqld；2) 端口 3306 是否监听且可达：本机 ss -tlnp，远程 telnet IP 3306；3) 远程连不上但本机正常：检查 bind-address 配置和云安全组；4) 认证失败：确认用户名密码、用户的 host 权限（user@'%' 还是 user@'localhost'）；5) 连接数满了报 too many connections：show processlist 看连接占用，必要时调大 max_connections 并排查连接泄漏。报错信息是关键：Connection refused 是网络/端口层，Access denied 是认证层，timeout 多半是防火墙。

## Linux 日志分析基础
系统日志位置：/var/log/messages 或 /var/log/syslog（系统级）、/var/log/secure（SSH 登录认证）、应用自己的日志目录。分析技巧：1) grep 关键字定位：grep -i error app.log；2) 按时间范围截取：sed -n '/10:00/,/11:00/p'；3) 统计频率：awk 排序统计 top N 错误类型；4) tail -f 实时观察问题复现。看日志先看时间线：问题发生时间点前后的日志才有价值，别从头翻。

## 排查问题的通用方法论
运维排查通用五步法：1) 确认现象：什么时间、什么范围、报什么错，先拿到准确的报错信息；2) 分层定位：按 DNS → 网络连通性 → 端口 → 应用服务 → 依赖组件的链路逐层排除；3) 对比变化："最近改了什么"是最重要的问题——发版、改配置、升配置都可能是诱因；4) 验证假设：每次只改一个变量，改完验证，避免多个变更叠加导致无法归因；5) 记录沉淀：把排查过程和结论记入知识库，下次同类问题直接复用。

## AI 运维助手工具使用边界说明
本助手的工具全部为只读检测（DNS/ping/端口/HTTP），不能执行修复操作。工具结果要结合知识库知识解读：ping 无回包可能是目标禁 ICMP 而非宕机；DNS 失败要先区分是单域名还是全域名问题；端口不通优先怀疑服务未启动。给出结论时必须基于工具真实返回，不能编造检测结果；对 rm、格式化、改防火墙等危险操作只给建议并提醒风险，不执行。
